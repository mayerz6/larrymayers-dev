# Larry Mayers Portfolio SaaS - Project Handoff

Last updated: 2026-11-05

## Purpose

This project is a custom PHP portfolio SaaS application. It is both a public professional portfolio and a private CMS/admin tool for managing structured career content.

The guiding idea is simple: build a credible public portfolio, then support it with SaaS-style admin workflows for content management.

## Current Product State

The application is a version 1.0 product:

- Public portfolio pages exist for home/profile, about, contact, resume, projects, and blog.
- Resume, project, and blog entries are database-driven and render publicly as card-based content.
- Admin authentication exists (single seeded user, session-based).
- A protected dashboard exists with a SaaS-style control center UI and live metrics (post/message/project/resume counts).
- Admin can manage resume entries, project entries, and blog posts (full CRUD on all three).
- Messages from the public contact form can be viewed and deleted from the admin area.
- The app uses SQLite for persistence.
- The frontend uses progressive JavaScript enhancement, not a frontend framework.
- A new `public/dev-projects/` area has appeared, containing a separate, independently-developed PHP application ("Cartana" / PriceCheck.io) with its own git history. See **Dev-Projects Area** below — this needs attention before it's safe to treat as "done."

## Dev-Projects Area (new, needs decisions)

`public/dev-projects/cartana/v1/` contains a separate, fully independent PHP application — a price-comparison / subscription SaaS product ("PriceCheck.io" per its `.env.example`), with its own `.htaccess`, `auth.php`, `config.php`, Stripe integration, and its own SQLite file (`products.db`). It has its **own nested git repository** pointing at `git@github-personal:mayerz6/Cartana.git`, with uncommitted local changes.

This proves the "self-contained subfolder" hosting pattern works mechanically (Apache's `-f`/`-d` passthrough in `public/.htaccess` lets any real file/folder bypass the portfolio's router entirely), but it currently has three unresolved problems:

1. **Session key collision risk.** Cartana's `auth.php` sets `$_SESSION['user_id']` and `$_SESSION['is_admin']` on login — the exact same session keys the portfolio's `Auth.php::requireAuth()` checks to gate `/dashboard` and all CMS routes. Both apps run on the same domain and would share the same PHP session cookie by default. A visitor logged into Cartana could be treated as an authenticated portfolio admin (or vice versa) without ever logging into the portfolio. **This needs to be fixed before Cartana goes live on the same domain.**
2. **Path/config mismatch.** Cartana's `config.php` defines `BASE_PATH` as `/projects/cartana/v1`, but its `.htaccess` `RewriteBase` is `/dev-projects/cartana/v1/`. These disagree.
3. **Repo hygiene.** The portfolio's `.gitignore` has a `projects/` rule (no match for `dev-projects/`), so `public/dev-projects/cartana/v1/` is currently fully unignored in the parent repo. If someone runs `git add -A` in the portfolio repo, git will likely add Cartana's nested `.git` as a broken gitlink (no real submodule config behind it) and could pick up `products.db` (real SQLite data). Needs an explicit decision: gitignore the folder, or set it up as a proper `git submodule`.

These are tracked as tickets in the backlog file.

## Security Note (public/ vs larrymayers-app/ split)

Separating the web-served `public/` directory from the application source, views, and SQLite files in `larrymayers-app/` is standard practice for exactly this stack, not just a Hostinger quirk. It is the same pattern Laravel (`public/`), Symfony (`public/`), and most modern PHP frameworks use by default. The reasons it matters here specifically:

- The web server's document root only ever needs to expose `index.php` and static assets. Nothing in `larrymayers-app/` (controllers, `Database.php`, the SQLite files, `views/*.php` with raw PHP in them) is reachable by a direct URL, because it's never inside the directory Apache serves from.
- If someone requests `/database/app.sqlite` or `/src/Core/Database.php` directly, there is no file at that path under `public_html` for Apache to return — the only thing that exists there is `index.php`, everything else is resolved through PHP includes using `__DIR__`-relative paths.
- It also protects against accidental source disclosure if PHP execution is ever misconfigured (e.g., a `.htaccess` mistake that causes `.php` files to be served as plain text) — only the small `public/` surface is exposed to that risk, not the whole app.

For this to hold in production, confirm on Hostinger: `database/app.sqlite` is genuinely not inside `public_html`, and `.htaccess` in `public_html` is actually active (some shared hosts disable `.htaccess` overrides by default per `AllowOverride`). Worth a one-time smoke test: try to load `https://larrymayers.site/../larrymayers-app/database/app.sqlite`-style paths and confirm they 404.
